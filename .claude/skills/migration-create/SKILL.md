# Migration Create

Creates a new database migration pair for a bounded context, edits both files with the schema change and its rollback, and (optionally) runs the project's verify/apply targets.

## When to use

- User says "add a migration for `<module>`" / "create a new table" / "alter X" / "drop the Y column" / "add an index on Z"
- A schema change is needed for one of the modules under `internal/`
- Do NOT use for data backfills as the only goal — those are typically scripts, not migrations. If a backfill is required *as part of* a schema change (e.g., adding a NOT NULL column), include it inside the same migration with the column add.

## Required information

Confirm with the user (ask only what's missing):

1. **Module** — bounded context that owns the affected schema (e.g., `account`, `organizations`, `credentials`, `workflows`). Must already exist under `internal/`. The Postgres schema name is identical to the module name.
2. **Migration name** — short snake_case description of the change. Imperative voice. Examples:
   - `add_users_table`
   - `add_email_index_to_users`
   - `alter_users_add_is_verified_column`
   - `drop_legacy_settings_column`
   - Avoid: dates, ticket IDs, vague verbs (`update_users`).
3. **Change details** — the actual SQL: which table(s), columns, constraints, indexes, FKs. Get specifics; don't infer.
4. **Rollback strategy** — how to undo the change. Some changes are not cleanly reversible (e.g., dropping a column with data). Surface this to the user; the down migration may have to be a no-op or recreate the structure without restoring data.

## Workflow

The skill drives Make targets — do NOT write files into `migrations/` directly.

### Step 1: Generate the file pair

```bash
make migration-create name=<migration_name> module=<module>
```

This invokes `<repo-root>/scripts/migration.sh create` which (run `make` targets from the repo root):
- Creates `internal/<module>/infrastructure/database/migrations/` if missing
- Writes `<TIMESTAMP>_<module>_<name>.up.sql` and `<TIMESTAMP>_<module>_<name>.down.sql`
- `<TIMESTAMP>` is `YYYYMMDDhhmmss` (UTC-ish, derived from `date +%Y%m%d%H%M%S`)
- Each file gets a 4-line header comment with the migration name and creation date

The generated header looks like:
```sql
-- Migration: <name>
-- Created: <human-readable date>

-- Write your UP migration SQL here
```

Capture the generated paths from the command output (the script prints them with `↑ UP:` / `↓ DOWN:` prefixes). You will need them in Step 2.

### Step 2: Fill in the SQL

Edit both files. The header comments stay; replace the `-- Write your ... here` placeholder with the actual statements.

**Up migration:** the actual schema change.
**Down migration:** the inverse, sufficient to return the database to its prior state.

See **SQL Conventions** below for the exact patterns expected by this project.

### Step 3 (optional): Dry-run verify

```bash
make migration-status module=<module>
```

This shows pending migrations for the module without applying them. Useful sanity check that the migration tool sees the new file.

### Step 4 (optional, only on user request): Apply

```bash
make migration-up module=<module>
```

This actually applies the migration to the database via Docker. **Do NOT run this without explicit user confirmation** — it mutates shared state (the dev database).

For rollback testing during development:
```bash
make migration-down module=<module>
```

## File path & naming (controlled by the script — do not override)

```
internal/<module>/infrastructure/database/migrations/
├── <TIMESTAMP>_<module>_<name>.up.sql
└── <TIMESTAMP>_<module>_<name>.down.sql
```

- The `<module>` segment is repeated inside the filename — this is intentional and lets sorted listings stay readable across modules.
- The timestamp is generated by the script; do NOT hand-pick it. If you need to reorder migrations relative to others, that's a real concern (the timestamp is the lexicographic ordering key) — surface it to the user.

## SQL conventions

The project uses **schema-per-module**: each module owns a Postgres schema with the same name (`account`, `organizations`, `credentials`, etc.). All tables live under `<module>.<table>`.

### Schema initialisation (one-time per new module)

If a module's first migration, the very first statement creates the schema:

```sql
CREATE SCHEMA IF NOT EXISTS <module>;
```

The matching down:

```sql
DROP SCHEMA IF EXISTS <module> CASCADE;
```

### Standard table layout

Every domain table includes UUID PK and the standard timestamp triplet:

```sql
CREATE TABLE IF NOT EXISTS <module>.<table> (
    id          UUID PRIMARY KEY,
    -- ... domain columns ...
    created_at  TIMESTAMP WITHOUT TIME ZONE DEFAULT (NOW() AT TIME ZONE 'UTC') NOT NULL,
    updated_at  TIMESTAMP WITHOUT TIME ZONE DEFAULT (NOW() AT TIME ZONE 'UTC') NOT NULL,
    deleted_at  TIMESTAMP WITHOUT TIME ZONE
);
```

Rules:
- **`id` is `UUID PRIMARY KEY`** — generated in the application layer (the domain's `New(...)` constructor calls `uuid.New()`), NOT a Postgres `DEFAULT gen_random_uuid()`.
- **All timestamps are `TIMESTAMP WITHOUT TIME ZONE`** with the `(NOW() AT TIME ZONE 'UTC')` default. Never `TIMESTAMPTZ` and never plain `NOW()` — the project standardises on UTC at the application boundary.
- **`deleted_at` is nullable** — soft-delete pattern; `NULL` means "active".
- **`created_at` and `updated_at` are `NOT NULL`** with the UTC default.
- **String types**: prefer `VARCHAR(N)` with an explicit length over `TEXT`. Common limits in this codebase: `VARCHAR(50)` for enums/roles, `VARCHAR(255)` for names/keys/titles.
- **Boolean columns** use `BOOLEAN NOT NULL DEFAULT FALSE` (or `TRUE` if that's the natural default). Always set a default; don't allow nullable booleans.

### Idempotency

- **Up migrations** use `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS` / `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`. The migration runner replays files on the migration record, so idempotency keeps re-runs safe.
- **Down migrations** use `DROP TABLE IF EXISTS` / `DROP INDEX IF EXISTS` / `ALTER TABLE ... DROP COLUMN IF EXISTS`. Same reasoning.

### Foreign keys

```sql
CREATE TABLE IF NOT EXISTS <module>.<table> (
    id          UUID PRIMARY KEY,
    user_id     UUID NOT NULL REFERENCES account.users(id) ON DELETE CASCADE,
    -- ...
);
```

- Cross-schema FKs are allowed (e.g., `organizations.users.user_id → account.users.id`) but be intentional: it couples the two modules at the DB layer. Confirm with the user that the coupling is wanted vs. enforcing the relation in application code.
- Pick `ON DELETE` semantics deliberately: `CASCADE` for child rows that lose meaning without the parent, `SET NULL` for soft references, `RESTRICT` (default) when the FK should block deletes.

### Indexes

Name indexes explicitly so the down migration is unambiguous:

```sql
CREATE INDEX IF NOT EXISTS idx_<table>_<column(s)> ON <module>.<table>(<column>);
```

- Naming: `idx_<table>_<col>` for single-column, `idx_<table>_<col1>_<col2>` for composite. Lowercase, underscore-separated.
- For unique constraints, `CREATE UNIQUE INDEX IF NOT EXISTS uq_<table>_<col>` (or use a `UNIQUE` constraint in the table definition for simple cases).

### Common patterns by change type

**Add a column:**

Up:
```sql
ALTER TABLE <module>.<table>
    ADD COLUMN IF NOT EXISTS <col> <type> NOT NULL DEFAULT <safe_default>;
```

Down:
```sql
ALTER TABLE <module>.<table>
    DROP COLUMN IF EXISTS <col>;
```

A `NOT NULL` column added to a populated table needs a `DEFAULT` (or a backfill) — Postgres will reject `NOT NULL` without one when existing rows exist. If the eventual goal is no default, do it in two migrations: (1) add with default, backfill, (2) drop the default.

**Add an index on an existing table:**

Up:
```sql
CREATE INDEX IF NOT EXISTS idx_<table>_<col> ON <module>.<table>(<col>);
```

Down:
```sql
DROP INDEX IF EXISTS <module>.idx_<table>_<col>;
```

For large tables, prefer `CREATE INDEX CONCURRENTLY` — but **note this cannot run inside a transaction**, which conflicts with most migration runners. Surface this to the user before using it; the project's runner may need a one-off out-of-band step.

**Drop a column** (irreversible — flag this):

Up:
```sql
ALTER TABLE <module>.<table>
    DROP COLUMN IF EXISTS <col>;
```

Down: there is no clean rollback once data is dropped. Options:
1. Recreate the column with the same type but `NULL` data (acceptable if the column was nullable to begin with).
2. Make the down a no-op with a comment explaining why.
3. Refuse to allow rollback by deleting the down file — but the migration runner expects a pair, so go with option 2 in practice.

```sql
-- Rollback: <name>
-- This migration drops a column; rolling back will not restore the data.
ALTER TABLE <module>.<table>
    ADD COLUMN IF NOT EXISTS <col> <type>;
```

**Rename a column** (best done as add+backfill+drop in production):

For dev/early-stage modules, a direct rename is fine:

Up:
```sql
ALTER TABLE <module>.<table> RENAME COLUMN <old> TO <new>;
```

Down:
```sql
ALTER TABLE <module>.<table> RENAME COLUMN <new> TO <old>;
```

For tables already deployed to production, do this in two migrations to avoid breaking the app between deploy and migrate: (1) add new column, dual-write in app, backfill; (2) drop old column.

## Critical rules

1. **Use Make targets — do not bypass the script.** `make migration-create` is the only sanctioned way to generate the file pair; the timestamp + filename + dual-file structure is part of the contract with the migration runner. Hand-rolling the files risks getting the order or naming wrong.
2. **Every up needs a matching down.** The script enforces the file pair; you fill both. A no-op down with an explanatory comment is acceptable when the change is genuinely irreversible.
3. **Do not edit migrations after they have been applied to a shared environment.** Once `migration-up` has run on staging or production, the file is part of history. Make a new migration to fix issues; never amend an applied one. If unsure whether it has been applied, ask the user.
4. **Schema name = module name.** Don't put `account` tables under the `public` schema or vice versa. The runner picks up files per-module from `internal/<module>/infrastructure/database/migrations/`.
5. **UUIDs come from the application** (`uuid.New()` in domain `New(...)` constructors), not from `gen_random_uuid()`. Don't add Postgres-side UUID defaults.
6. **All timestamps are UTC `TIMESTAMP WITHOUT TIME ZONE`.** Never `TIMESTAMPTZ`.
8. **Do not run `migration-up` autonomously.** It mutates shared state. Always confirm with the user before applying. `migration-status` (dry-run) is safe to run.

## Final steps

After both files are filled in:

1. Re-read both `.up.sql` and `.down.sql` end-to-end. Mental dry-run: run up, then down, then up — does the schema return to the expected state at each step?
2. (Optional, safe) `make migration-status module=<module>` — confirms the file is picked up.
3. (Optional, requires user confirmation) `make migration-up module=<module>` to apply.
4. If the migration adds tables/columns that domain code references, the matching domain entity, repository, and any new sentinels need to exist. Surface this to the user as the next step — migration alone doesn't ship a feature.

## What NOT to do

- Do NOT write `.sql` files directly under `migrations/` without using `make migration-create`. The timestamp + dual-file naming is the runner's contract.
- Do NOT pick the timestamp manually. If two migrations need a specific order, run `make migration-create` for them in that order — the script's `date` call handles uniqueness.
- Do NOT use `TIMESTAMPTZ`, `gen_random_uuid()`, or `now()` (without the UTC cast). The project's UTC standard is at the database layer for a reason.
- Do NOT include data backfills that span millions of rows in a single migration without batching. Migrations run inside a transaction by default; long-running migrations lock tables and stall deploys. Surface large backfills as a separate concern.
- Do NOT mix multiple unrelated changes in one migration. One logical change per migration; the file is cheap, the rollback story stays clean.
- Do NOT skip the down migration "because we'll never roll back". Every developer who runs `make migration-down` for local cleanup expects it to work.
- Do NOT run `make migration-up` without explicit user confirmation, even on dev — the Docker container connects to a real database.
